# NFCKit

マイナンバーカードの IC チップを Core NFC で読み取る iOS SDK です。

## 用語

IC カードとの通信に出てくる言葉を、このリポジトリで実際に使うバイト列を例に説明します。

### 全体の関係

```
アプリ ──コマンド APDU（お願い）──▶ カード
       ◀─レスポンス APDU（返事）──
                   ├ データ：BER-TLV で書かれている（証明書なら X.509）
                   └ ステータスワード：成功か失敗か
```

アプリとカードの会話は、「お願い」と「返事」の繰り返しです。

- **APDU**：お願いと返事の「書式」
- **ステータスワード**：返事の最後に付く「結果のコード」
- **BER-TLV**：返事の中身の「書き方」
- **X.509**：BER-TLV で書かれた「証明書」の決まり

### カードの中身（AP・DF・EF・AID）

IC カードの中は、パソコンのフォルダとファイルのような木の形になっています。

```
MF（いちばん上のフォルダ）
├── 公的個人認証 AP              ← フォルダ（DF）。名前は AID
│   ├── EF 000A：利用者証明用電子証明書   ← ファイル（EF）
│   ├── EF 0018：利用者証明用の暗証番号
│   └── …
├── 券面事項入力補助 AP
└── …
```

| 用語 | ひとことで | 例 |
| --- | --- | --- |
| AP（アプリケーション） | カードの中の「用途ごとのアプリ」 | 公的個人認証 AP |
| DF（Dedicated File） | フォルダ。AP は DF として入っている | 公的個人認証 AP |
| EF（Elementary File） | 中身のあるファイル。2 バイトの番号で呼ぶ | `00 0A` |
| AID（Application Identifier） | AP の世界で一つだけの名前 | `D3 92 F0 00 26 01 00 00 00 01` |

「AP を選ぶ → EF を選ぶ → 中身を読む」は、ターミナルで `cd` してから `cat` するのと同じ流れです。

### APDU（Application Protocol Data Unit）

カードとの会話 1 往復分の書式です。アプリが送るものを **コマンド APDU**、カードが返すものを **レスポンス APDU** と呼びます。

#### コマンド APDU（お願い）

```
┌────┬────┬────┬────┬────┬──────────┬────┐
│CLA │INS │ P1 │ P2 │ Lc │ データ    │ Le │
└────┴────┴────┴────┴────┴──────────┴────┘
 ←── 必ず付く 4 バイト ──→ ←──── 必要なときだけ ────→
```

| 欄 | 意味 | 例 |
| --- | --- | --- |
| CLA | 命令のおおまかな種類。このリポジトリでは常に `00` | `00` |
| INS | 何をしてほしいか | `A4` 選ぶ、`B0` 読む、`20` 暗証番号を照合する |
| P1・P2 | 命令ごとの細かい指定 | 「名前で選ぶ」「番号で選ぶ」、読み始める位置 |
| Lc | 送るデータが何バイトか | 10 バイトなら `0A` |
| データ | 送る中身 | AID、EF の番号、暗証番号 |
| Le | 返してほしいデータの最大バイト数 | `04` は 4 バイト、`00` は 256 バイト |

Lc と Le があるかないかで、形が 4 通りに分かれます。

| ケース | 形 | 使う場面 |
| --- | --- | --- |
| 1 | 4 バイトだけ | 暗証番号の残り回数を聞く（データなしの VERIFY） |
| 2 | 4 バイト ＋ Le | ファイルを読む（READ BINARY） |
| 3 | 4 バイト ＋ Lc ＋ データ | AP や EF を選ぶ（SELECT）、暗証番号を照合する |
| 4 | 4 バイト ＋ Lc ＋ データ ＋ Le | データを送り、データも受け取る |

利用者証明用電子証明書を読むときは、次の順に送ります。

```
00 A4 04 0C 0A D3 92 F0 00 26 01 00 00 00 01   公的個人認証 AP を名前（AID）で選ぶ
00 A4 02 0C 02 00 0A                            証明書の EF を番号で選ぶ
00 B0 00 00 04                                  先頭から 4 バイト読む（全体の長さを知るため）
00 B0 00 04 FF                                  4 バイト目から 255 バイト読む（以降も同じように続ける）
```

READ BINARY では、P1 と P2 の 2 バイトが「何バイト目から読むか」を表します。使えるのは 15 ビット分なので、指定できる位置は 0〜32767 です。

#### レスポンス APDU（返事）

```
┌────────────────┬─────┬─────┐
│ データ（任意）  │ SW1 │ SW2 │
└────────────────┴─────┴─────┘
                  └ ステータスワード ┘
```

### ステータスワード（SW1・SW2）

返事の最後に必ず付く 2 バイトの結果コードです。Web の `200` や `404` と同じ役割です。

| 値 | 意味 |
| --- | --- |
| `90 00` | うまくいった |
| `63 CX` | 暗証番号が違った、または残り回数を聞かれた。**X が残りの回数** |
| `69 83` | 暗証番号がロックされている |
| `69 82` | 条件を満たしていない（たとえば、先に暗証番号が必要） |
| `6A 82` | 選んだ AP やファイルが見つからない |

`63 CX` は、2 バイト目の上半分が `C`、下半分が回数です。`63 C2` なら残り 2 回です。

### BER-TLV

返事の中身を書くためのルールです。どのデータも「種類（Tag）・長さ（Length）・中身（Value）」の 3 つ組で書きます。

```
┌─────┬────────┬──────────────┐
│ Tag │ Length │ Value        │
└─────┴────────┴──────────────┘
 何か    何バイト    中身
```

中身の中に、さらに 3 つ組を入れることができます。荷物の箱の中に、ラベル付きの小箱がいくつも入っているイメージです。

```
30 0A                    ← 箱（SEQUENCE）。中身は 10 バイト
   02 01 05              ←   数（INTEGER）。1 バイト。値は 5
   0C 05 48 65 6C 6C 6F  ←   文字（UTF8String）。5 バイト。"Hello"
```

#### 種類（Tag）

先頭の 1 バイトのビットにも意味があります。いちばん大事なのは、右から 6 番目のビット（`0x20`）です。ここが 1 なら「中にさらに 3 つ組が入っている箱」です。

| Tag | 意味 | 箱か |
| --- | --- | --- |
| `30` | SEQUENCE（順番のある並び） | 箱 |
| `31` | SET（順番のない集まり） | 箱 |
| `A0` | 文脈で意味が決まる [0] | 箱 |
| `02` | INTEGER（数） | 中身 |
| `06` | OID（項目の種類を表す番号） | 中身 |
| `13`・`0C` | 文字列 | 中身 |

#### 長さ（Length）

| 先頭のバイト | 読み方 | 例 |
| --- | --- | --- |
| `00`〜`7F` | そのまま長さ | `05` は 5 バイト |
| `81` | 次の 1 バイトが長さ | `81 C8` は 200 バイト |
| `82` | 次の 2 バイトが長さ | `82 06 26` は 1574 バイト |

証明書の先頭は `30 82 XX XX` です。この 4 バイトを読めば全体の長さが分かるので、最初に 4 バイトだけ読んでいます。

#### DER

DER は、BER の書き方を 1 通りに絞ったものです（たとえば、長さは必要最小限のバイト数で書く）。証明書は DER で書かれていますが、DER は BER の一種なので、BER を読む仕組みでそのまま読めます。

### X.509

電子証明書の世界共通の形式です。HTTPS で使われる証明書と同じ形式で、マイナンバーカードの電子証明書もこれです。中身は DER の箱の入れ子です。

```
証明書                       30
├── 署名される本体            30
│   ├── バージョン            A0（省略できる）
│   ├── シリアル番号          02   ← 取り出す
│   ├── 署名の方式            30
│   ├── 発行者                30   ← 取り出す
│   ├── 有効期間              30
│   │   ├── 始まり            17 か 18
│   │   └── 終わり            17 か 18   ← 取り出す（有効期限）
│   ├── 持ち主                30
│   ├── 公開鍵                30
│   └── 拡張                  A3
├── 署名の方式                30
└── 署名                      03   ← 発行者（J-LIS）が本体に付けた署名
```

#### シリアル番号

発行者が証明書ごとに付ける番号です。数（`02`）として書かれているので、先頭が `00` のことがあります。これは「マイナスの数ではない」ことを示すためだけのバイトなので、取り除いて表示します。

本人と結び付く値なので、`print` しても `****` としか出ないようにしています。

#### 発行者

「どこが発行したか」です。発行者は 3 段の箱になっています。

```
発行者                   30（SEQUENCE）
├── まとまり              31（SET）
│   └── 項目              30（SEQUENCE）
│       ├── 種類          06（OID）55 04 06 ＝ 国
│       └── 値            13（文字列）"JP"
├── まとまり              31
│   └── 項目              30
│       ├── 種類          06（OID）55 04 0A ＝ 組織
│       └── 値            13 "JPKI"
└── …
```

1 つの「まとまり（SET）」には項目を複数入れられる決まりなので、読むときは「まとまり」と「項目」の 2 段でたどります。

| OID | 意味 | 表示 |
| --- | --- | --- |
| `55 04 03` | 名前 | CN |
| `55 04 06` | 国 | C |
| `55 04 0A` | 組織 | O |
| `55 04 0B` | 部署 | OU |

#### 有効期限

時刻は 2 通りの書き方があります。どちらも最後の `Z` は「世界標準時（UTC）」という意味です。日本時間に直すと 9 時間進みます。

| Tag | 書き方 | 例 |
| --- | --- | --- |
| `17`（UTCTime） | 年が 2 桁：`YYMMDDHHMMSSZ` | `310101000000Z` は 2031 年 1 月 1 日 0 時 |
| `18`（GeneralizedTime） | 年が 4 桁：`YYYYMMDDHHMMSSZ` | `20500101000000Z` は 2050 年 1 月 1 日 0 時 |

年が 2 桁のときは、50 以上なら 1900 年代、49 以下なら 2000 年代と読みます。

画面に出す有効期限は、カードに書かれた期限です。期限内でも、失効しているかどうかはサーバーで J-LIS に問い合わせないと分かりません。

### 命令（SELECT・READ BINARY・VERIFY）

| 命令 | INS | すること | 例えると | 暗証番号の残り回数 |
| --- | --- | --- | --- | --- |
| SELECT | `A4` | AP や EF を選ぶ | `cd` | 減らない |
| READ BINARY | `B0` | 選んだ EF の中身を読む | `cat` | 減らない |
| VERIFY | `20` | 暗証番号を照合する。データを付けなければ残り回数を聞くだけ | ログイン | **違う暗証番号を送ったときだけ減る** |

利用者証明用電子証明書の読み取りでは、VERIFY を一度も送りません。そのため、何度試しても暗証番号の残り回数は減りません。
